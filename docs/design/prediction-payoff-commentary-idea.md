## 動機

今の実況（パス1・`src/pipeline.py`のイベント駆動生成）は「その時点までに起きた
ことしか渡さない」設計で、意図的にネタバレゼロにしている（詳細:
[[project_battle_situation_reasoning]]・`.claude/skills/video-commentary/SKILL.md`の
ネタバレ検査工程）。これはこれで正しい設計だが、人間の実況者がやる
「布石→回収」の演出（予言してみせて、当たった/外れたで盛り上げる）が原理的にできない。

## 検討した方式と却下理由

### ❌ 方式A: 1試合分を丸ごと1回のプロンプトに渡して一括生成

「1試合の内容を一気に渡して実況文生成できないか」という発想から出発したが、以下の
理由で却下:

1. **ネタバレ防止が崩れる**: 序盤の実況を作る時点でLLMが勝敗・全展開を知ってる状態に
   なる。「未来のことは言わないで」と指示はできてもモデルの指示追従に100%は賭けられない
2. **タイムスタンプ整合の失敗リスク**: 今は「1イベント=1回の呼び出し=1〜2文」で
   Python側が秒数を確定させるだけの単純な構造。一括生成だと「N件ぶん、順番も数も
   内容もズレず返す」ことをLLMの出力精度に賭けることになり、1件でもズレると
   動画全体の整合検証が面倒になる
3. **失敗時の被害範囲**: 今は1イベント1回なので1件コケても他は無事。一括だと
   生成の脱線が試合全体を巻き込む
4. **「実況っぽさ」の劣化**: リアルタイム実況の臨場感は「その瞬間まで何が起きたか
   しか知らない」ことに支えられている。まとめて生成すると後知恵っぽい不自然な
   言い回しが出やすい

### ✅ 方式B（推奨）: パス1本体は変えず、「予測→回収」ペアだけを後付けで注入する新パス

`fillers.jsonl`（無言埋めフィラー・パス1.5）・`bubbles.jsonl`（プレイヤー吹き出し）と
**同じ「1試合分の情報が揃った後付けで、特定の時刻に差し込む」既存パターン**を流用する。
パス1のイベント駆動リアルタイム実況には一切手を入れない。

```
パス1完了後（manifest.jsonl・timeline.jsonl・states.jsonl が揃った状態）
  ↓
新パス「predictions生成」: 1試合分の情報をまとめてLLMに見せて
  「序盤の材料から見て面白い予想ポイントを1〜2個選び、
   ①予測セリフ＋その時刻 ②結果が出た時点の回収セリフ＋その時刻」
   をJSONで返させる
  ↓
predictions.jsonl として保存 → パス2合成時にfillers/bubblesと同様に挿入
```

**具体例（`renders/2026-08-18_22-24-52`なら）**:
- t=249.4s（ペリッパーのおいかぜ直後）「これはおいかぜでそのまま押し切るか…！」（予測）
- t=499.2s（battle_end）「あー、おいかぜは活きたけど最終的には競り負けちゃったか…」（回収・外れ）

この方式のメリット:
- パス1は無変更＝既存のネタバレ検査（`check_spoilers.py`）の対象範囲を広げなくて済む
- 合成基盤（fillers/bubblesの挿入・タイムスタンプ衝突回避）をそのまま再利用できる
- 1試合1〜2本程度に絞れば「予言者ムーブ」がくどくならない

## 実装時に決めるべきこと（保留中の未決事項）

1. **1試合あたり何本？**（多すぎるとくどい。1〜2本が無難という仮説）
2. **回収のタイミング**: 明確な「結果」イベント（faint/battle_end等の近く）に紐付けるのが自然
3. **外れ演出も込みで作る**: 的中率100%だと不自然なので「外した」体のセリフも
   LLMに選ばせる（当たり/外れの判定自体は1試合分の情報が揃ってるPython側で機械的に
   判定できるはず＝LLMには「これは当たった/外れた」を事実として渡し、演技だけさせる）
4. **`--persona neutral`運用中でも成立する言い回しにする**（他の新機能と同じ制約。
   詳細: [[project_video_first_policy]]）
5. 新スクリプト名の案: `scripts/generate_predictions.py`（パス1.5と同じ並びのパス想定）
