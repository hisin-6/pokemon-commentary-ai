# ADR-003: 実況文生成にローカルLLM（Phi-3 mini 4bit量子化）を使用する

## ステータス
承認済み

## 日付
2026-02-24

## 文脈

実況文の生成は毎ターン必要であり、APIを毎回呼び出すとコストが積み重なる。一方でローカルLLMはVRAMを消費するため、3Dモデルの描画（4〜5GB）と共存できるモデルを選ぶ必要がある。

## 決定

Phi-3 mini（4bit量子化）をOllamaでローカル実行し、実況文を生成する。

## VRAM配分

| コンポーネント | 消費VRAM |
|--------------|---------|
| Phi-3 mini 4bit量子化 | 約2〜3 GB |
| 3Dモデル描画 | 約4〜5 GB |
| YOLO・OCR | 約0.5〜1 GB |
| 余裕 | 約1〜3 GB |
| **合計** | **10GB以内** |

## 理由

- 4bit量子化によりVRAM消費を抑えながら十分な文章生成品質を確保できる
- Ollamaにより簡単にローカル実行できる
- 実況文生成のみであればPhi-3 miniクラスで実用的な品質が出る
- 毎ターン呼び出してもAPIコストが発生しない

## 却下した選択肢

| 選択肢 | 却下理由 |
|--------|---------|
| Llama 3.1 8B（量子化なし） | VRAM 5〜6GB消費で3Dモデルと共存が厳しい |
| 毎回Bedrock APIで生成 | ターン数が多くコスト過大になる |
| Gemma 2 9B | Phi-3 miniより消費VRAMが大きい |

## 再検討条件

実況の品質がユーザー要件を満たさない場合は、以下を検討する。

- Llama 3.1 8B 4bit量子化に切り替える（VRAM約4〜5GB）
- 実況文生成もBedrock Claude Haikuに移行する

## 結果

RTX 3080（VRAM 10GB）の範囲内で3Dモデルと安定して共存できる。毎ターンのAPI呼び出しコストをゼロに抑えられる。

## 追記（2026-08-04）: 「再検討条件」が発動し、Phi-3 miniはフォールバック専用に降格

上記「再検討条件」に記載していた「実況文生成もBedrock Claude Haikuに移行する」が実際に発動した
（ADR-001参照）。現状は **Bedrock Claude Haikuが実況文生成を含めて優先的に呼ばれ、Phi-3 miniは
Bedrock呼び出しが失敗した時のみのフォールバック**という役割に変わっている
（`src/pipeline.py`の`_dispatch_commentary`: `bedrock_commentary`があればそれを採用、
無ければPhi-3にフォールバック）。ADR-001「実況文生成はADR-003（ローカルLLM Phi-3 mini）が
担当する」という当初の責務分担も、この時点で実態と乖離している（ADR-001側にも追記予定）。

### VRAM前提の訂正: 「Phi-3 mini + 3Dモデル同時稼働」は今は起きない

本ADR策定時（2026-02）はライブ配信前提で、Phi-3 mini（実況文生成）とバーチャルモーション
キャプチャー（3Dモデル描画）が常時同時稼働する想定でVRAM表を組んでいた。
ADR-009（2026-07-13・動画ファースト方針）以降、パイプラインは**フェーズが分離**しており、
この前提が崩れている。

| フェーズ | 稼働コンポーネント | VRAM実測目安 |
|---------|-------------------|------------|
| パス1（解析・実況生成） | EasyOCR(0〜0.5GB) + YOLO(0.5〜1GB) + Bedrock(クラウド・VRAM消費なし) | **約1〜1.5GB** |
| v2c（アバター録画） | バーチャルモーションキャプチャー（4〜5GB）のみ。OCR/YOLOはこの時点で稼働終了済み | **約4〜5GB** |

さらにPhi-3 mini/Ollamaは現在フォールバック専用で滅多に呼ばれないため、Ollamaの既定動作
（アイドル数分でモデルを自動アンロード）により**常駐すらしていない**のが実態。

結果として、パス1実行中は最大 **約8.5GB がローカルLLM用に未使用のまま空いている**
（VMCと同時稼働させない前提なら）。「ローカルLLM移行」ロードマップ（改善ロードマップ⑦）を
検討する際は、旧VRAM表（Phi-3 mini 2〜3GB枠固定）ではなくこちらを前提にすること。

## 追記（2026-08-04その2）: フォールバックモデルをPhi-3 mini→gemma2:9bへ変更

上記のVRAM余裕を踏まえ、`scripts/compare_local_llm_commentary.py`（新規作成）で
Llama-3.1-Swallow-8B-Instruct・qwen2.5:7b/14b・gemma2:9b・phi3.5の5モデルを、
くれぴのキャラ設定＋用語集＋ダブル戦術知識＋few-shot例文を含むフルプロンプトで比較した。

**結果**:
- qwen2.5:14bは実機VRAM実測で9015MiB使用（空き約1.2GB）。パス1中はEasyOCR/YOLOと
  同時稼働するため合計10GBを超えるリスクが高く**除外**。加えて実際の生成で
  ロシア語/中国語混入のグリッチが1回発生し信頼性面でも除外
- Swallow-8B-Instructは事実関係は正確だが、です・ます調のアナウンサー口調になり
  くれぴのタメ口・♪多用のキャラ性と大きく乖離。**除外**
- phi3.5は自分/相手の帰属を誤る重大なミスが発生（相手のポケモンを「我が」と
  言う等）。**除外**
- qwen2.5:7bも技の使い手を取り違えるミスが発生。**除外**
- gemma2:9b（VRAM 5.4GB）が事実関係・キャラ性ともに最も安定していたが、
  複数回の再テストで「前ターンの出来事を今起きたかのように話す」ミスや
  軽微なタメ口崩れ（「〜わね」）が残存

**結論**: どのローカルモデルもBedrock Claude Haikuを置き換えるレベルの正確性・
キャラ一貫性には未到達（本番の主実況をローカルに移す判断はまだ早い）。
一方、**フォールバック用途**（Bedrock呼び出し失敗時のみ発火する安全網。粗があっても
実害が小さい）としては、現行のPhi-3 miniより明確に上回るgemma2:9bへの置き換えが
妥当と判断し実施した：

- `src/commentary/phi3_client.py`: `MODEL_NAME`を`phi3:mini`→`gemma2:9b`に変更。
  クラス名/ファイル名は`pipeline.py`側の互換性維持のため`Phi3Client`/`phi3_client.py`の
  まま据え置き（歴史的名称であることをdocstringに明記）
- プロンプトはくれぴのキャラ設定・用語集・ダブル戦術知識・出力ルール
  （「了解しました」指示エコー対策・前ターン振り返り禁止等）を含むフル版に刷新。
  内容は`src/commentary/kurepi_persona.py`（新規）に切り出し、比較スクリプトと
  フォールバッククライアントの両方から共有する単一ソースにした
- `generate_commentary()`に`battle_context`引数を追加（`BattleStateTracker.to_context()`の
  戦況サマリー）。従来は生OCRテキストしか渡していなかったが、比較検証で
  「構造化された戦況情報が無いと精度が大きく落ちる」と判明したため、`pipeline.py`の
  2箇所の呼び出し元（ライブ経路・動画モード後付け生成経路）も合わせて更新した

VRAM: 5.4GB（gemma2:9b）+ 1〜1.5GB（EasyOCR/YOLO） = 6.4〜6.9GBで、10GB上限に対し
3GB以上の余裕を確保。
