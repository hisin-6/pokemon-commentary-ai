# ADR-009: 実況動画ファースト方針を採用する（ライブ配信は後段）

## ステータス
承認済み（2026-07-13）

## 日付
2026-07-13

## 文脈

本プロジェクトの最終形はライブ配信でのリアルタイム実況だが、ライブモードには以下の構造的な課題がある。

- **実況処理中のフレーム喪失**: Bedrock呼び出し〜音声再生の処理ブロック中（約12秒）に画面キャプチャが止まり、1試合あたり約1ターンぶんのイベントを取りこぼす（Sprint 7で実測。4試合動画の降参ターン欠け等）。根本解決には処理の非同期化などの大掛かりな改修が必要
- 遅延目標（イベント検知〜音声再生開始 < 15秒）を守るための制約が、認識精度・実況品質の改善と競合する

一方、動画ファイル入力（`--input`）では全フレームを処理でき、フレーム喪失は発生しない。Sprint 7 で戦況認識の精度は大きく向上しており（ターン検出37/38・気絶漏れゼロ・HP追跡が書き起こしとほぼ一致）、まず「録画した対戦動画をうまく実況できる」品質に到達させることが、ライブ実況の品質向上にもそのまま繋がる。

## 決定

当面の開発ターゲットを**録画済み対戦動画への実況付与（実況動画の制作）**とする。

- 入力は録画済みの対戦動画ファイル（`--input`・動画モード）を正とする
- ライブモード（OBS仮想カメラ入力）のコード・起動オプションは削除せず残すが、ライブ特有の課題（処理ブロックによるフレーム喪失の非同期化対応等）への改修は**凍結**する
- 実況動画の品質が満足できるレベルに達した後に、ライブ配信対応（非同期化等）を再開する

## 影響

### 適用外となる既存の目標・制約

| 既存の記述 | 扱い |
|-----------|------|
| 「イベント検知から音声再生まで3秒以内」（システム設計書・設計原則） | 動画モードでは**適用外**。処理時間は成果物（実況動画）の品質に影響しない |
| 「イベント〜音声再生開始 < 15秒」（ADR-007・遅延目標） | 同上。ライブ再開時の目標として据え置き |
| ライブモード処理ブロック問題（フレーム喪失） | 動画モードでは発生しない。**優先度低下**（ライブ再開時に再着手） |

### 変わらないもの

- イベント駆動アーキテクチャ（ADR-007）の検知・蓄積・生成の流れ自体は動画モードでも同一
- デバウンス秒数などの時間ベースのロジックは動画内時間で機能するため変更不要
- VRAM 10GB制約・EC2経由のAWSキー管理・Bedrockコスト抑制方針は据え置き

### 新たに必要になる工程（今後の課題・未実装）

実況動画として成立させるために、以下の合成工程が必要になる。

1. **実況音声の動画タイムライン同期**: 生成した実況音声を、元動画のイベント発生時刻に対応する位置に配置して合成する仕組み（現状は生成時に即時再生するのみで、動画内時刻との対応付けは未実装）
2. **アバター映像との合成**: 3Dモデル（バーチャルモーションキャプチャー）の口パク映像を元動画と合成する制作フロー

## 却下した選択肢

| 選択肢 | 却下理由 |
|--------|---------|
| ライブモードの非同期化を先に実装 | 実況品質の検証・改善が先。品質が未達のままライブ基盤に工数を割いても成果に繋がらない |
| ライブと動画制作の二正面開発 | リソース分散。動画モードでの品質改善はライブにもそのまま活きるため、順番に進める方が効率的 |

## 結果

処理時間の制約から解放され、認識精度・実況文品質・音声品質の改善に集中できる。動画モードは全フレーム処理のためライブより検出条件が良く、まず動画で品質を確立してからライブ特有の課題（フレーム喪失・遅延）に取り組む段階的な進め方が可能になる。

## 追記（2026-07-13）: 合成方式の決定 — 2パス方式＋高密度実況

### 2パス方式（決定）

**パス1（解析・素材生成）**: 既存パイプラインの動画モードに素材出力モードを追加する。

- 実況音声を即時再生する代わりに（or 加えて）WAVをファイル保存
- マニフェスト（JSONL）に1行追記: `{event_time: イベント検知時点の_video_now, event_type, commentary, wav_path, duration}`
- イベント時刻は`_video_now`（フレーム位置÷fps・`src/pipeline.py`実装済み）を使う。動画モードでは処理時間が動画内時刻を汚さないため正確

**パス2（合成）**: 新スクリプト（`scripts/render_commentary_video.py`想定）。

- マニフェストを読み、スケジューリング（かぶり解決）→ 無音ベースの実況トラック1本を構築 → ffmpegで元動画とミックス
- **かぶり解決**: `max(イベント時刻, 前の実況の終了+ギャップ)`に配置。ライブ実装の「前の再生を停止して割り込み」とは異なり、動画では全部言い切る。イベントから遅れすぎた実況のみ破棄。密集区間はVOICEVOX `speedScale`で話速調整も可
- **ダッキング**: 実況中はゲーム音量を下げる（ffmpeg）
- 合成パスが独立しているため、配置ポリシー変更時にBedrock再課金なしで作り直せる（2パスにする最大の理由）
- アバター映像はv1スコープ外（v1=ゲーム映像＋実況音声で完成。v2で完成トラックをCABLE Inputに等速再生→VMC口パクをOBS録画→ワイプ合成）

### 高密度実況（「間」を作らない）方針

動画では無言の間が品質を直接下げるため、しゃべり密度を優先する。手段は安い順に:

1. **各イベント実況を長めに生成**: 出力トークンは安価（+200トークンで約+0.15円）。プロンプト指示の変更のみ
2. **台本パス（ギャップフィラー）**: 解析完了後、試合全体のイベントログ・戦況をテキストのみ（画像なし）でBedrockに1回渡し、実況が途切れる区間用の小ネタ（控えの紹介・戦況整理・雑談）をまとめて生成して間に配置する。**その時点までに判明している情報しか使わない（ネタバレ禁止）指示が必須**
3. さらに埋まらない間はテンプレ文/ローカルPhi-3（無料）

### フェーズ計画とv2の動画レイアウト（2026-07-13 決定）

| フェーズ | 完成形 | 内容 |
|---------|--------|------|
| **v1** | 実況音声入りmp4 | ゲーム映像＋ゲーム音＋実況音声（枠・アバターなし） |
| **v2** | 枠＋アバター入りmp4 | 下記レイアウトを適用し、アバター映像（VMC口パク録画）をワイプ合成 |

**v2のレイアウトは「biim風＋戦況パネル」を基本とする**（モックアップ: `docs/design/frame-mockups/mockup_A_biim.png`）。

- 構成: ゲーム画面（左上・縮小）＋下部に実況テキストの字幕帯（音声とシンクロ表示）＋右サイドに戦況パネル（両陣営HPバー・技ログ・ターン数）＋右下にアバター
- パネルの表示データはすべて`BattleStateTracker`の認識結果から自動生成する（手作業の編集なし）
- **レイアウトは変更容易な設計とする**: 枠は合成パスのレンダリング層に閉じており、解析結果（マニフェスト・戦況データ）と分離しているため、枠の変更・改善は再レンダリングのみで可能（Bedrock再課金なし）。検討済みの代替案（スポーツ中継風・AI認識モニター・実況ブース風）のモックアップも`docs/design/frame-mockups/`に保存済みで、特に「AI認識モニター」パネル（`mockup_C_ai_brain.png`）は案Aと構造が同じため後からの差し替え・併用が容易

### コスト見積もり（Bedrock Claude Haiku 4.5: 入力$1/出力$5 per MTok・150円/$）

| 項目 | トークン | 費用 |
|------|---------|------|
| イベント実況1回（画像800×450≈480tok込み・実測入力1,240/出力85） | — | 約0.25円 |
| 同・実況文を3倍に増量 | 出力+200tok | +0.15円 |
| 1試合のイベント実況（約30回・増量込み） | — | 約10円 |
| 台本パス（テキストのみ・入力5K/出力1.5K） | — | 約2円 |
| **1試合合計** | | **約10〜15円** |

動画100本作っても1,000〜1,500円程度。コストは意思決定の制約にしない。合成パスのやり直しは課金ゼロ（パス1の再実行のみ課金）。必要になればBedrockのprompt caching（読み取り約0.1倍）でさらに下げられるが、この規模では不要と判断。
