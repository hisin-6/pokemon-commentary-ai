# ADR-005: AWSはBedrock・EC2を使用する（S3は2026-11-26に廃止）

## ステータス
承認済み（2026-11-26改訂：S3の役割を廃止）

## 日付
2026-02-24（改訂: 2026-11-26）

## 文脈

開発者はすでにEC2とS3を利用している。AIサービスの追加とAPIキーの安全な管理、ログの保存先が必要。

## 決定

以下の役割分担でAWSを利用する。

| サービス | 役割 |
|---------|------|
| AWS Bedrock | Claude Haiku Vision・テキスト生成のAPI呼び出し |
| EC2 | APIキー管理・Bedrockへの中継サーバー（Flask） |
| ~~S3~~ | ~~実況ログ・スクリーンショットの保存~~ → **2026-11-26廃止**（下記「改訂履歴」参照） |

## アーキテクチャ

```
ローカルPC
　↓ 画像・状況テキストを送信
EC2（Flask）
　↓ Bedrockを呼び出す
AWS Bedrock（Claude Haiku）
　↓ 実況テキストを返却
ローカルPC（VOICEVOX・3Dモデル）
```

※実況ログ・診断JSONLはローカル（`renders/` 等）に保存する。S3には保存しない。

## 理由

- EC2にAPIキーを置くことでローカルPCにキーを持たずセキュリティが向上する
- 既存のEC2の知識をそのまま活用できる
- BedrockによりAWSの請求に一本化でき管理が容易
- LambdaなどよりEC2の方が学習コストが低く既存環境と親和性が高い

## 却下した選択肢

| 選択肢 | 却下理由 |
|--------|---------|
| Lambda（中継サーバー） | 学習コストあり・初期段階では不要 |
| Rekognition | ゲーム画面への適合性が不明 |
| ローカルからBedrock直接呼び出し | APIキーをローカルに置くリスクがある |

## 注意事項

- **AWSの請求アラートを最初に設定すること**（コスト超過防止）
- EC2インスタンスは常時起動にせず、開発・実況時のみ起動する運用を推奨

## 結果

既存のAWS環境を活用しながら安全にAIサービスを追加できる。Sprint 2でEC2サーバーの構築とBedrock連携を実装する。

## 改訂履歴

### 2026-11-26: S3の役割を廃止

**経緯**: 2026-11-24のAWS/EC2セキュリティ点検で、S3保存用の `POST /api/log` エンドポイントをパイプラインから一度も呼んでいないことが判明した。systemdユニットの `S3_BUCKET` もプレースホルダー（`your-bucket-name`）のままで、S3は実質使われていなかった。

**決定**:
- `src/api/server.py` から `/api/log`・S3クライアント・`S3_BUCKET`/`S3_REGION` 設定を削除する
- EC2ロールの権限は Bedrock（Claude Haiku 4.5）の `InvokeModel` のみに絞る（2026-11-24適用済み・インラインポリシー `pokemon-api-bedrock-invoke-only`）
- 実況ログ・診断データはローカルに保存する（実況動画ファースト方針・ADR-009で必要なデータはすべてローカルの `renders/` 配下にある）

**理由**: 使っていない機能のために権限を残すと、EC2が侵害されたときの被害範囲が広がる。最小権限の原則に合わせる。

**将来S3が必要になったら**: このADRを再改訂してから、用途に合わせた最小権限のポリシー（特定バケット・特定プレフィックスへの `PutObject` のみ等）を追加する。
